00 What you'll build & how it fits together ▾

Read this first · 4-minute orientation

PlayTools has a meta-game called The Rig — a persistent "NetCoin mining rig" / gaming battlestation that the player builds out over weeks. Players earn NetCoin (an in-app currency) and spend it in the NetStore on Rig Items: GPUs, chairs, monitors, posters, RGB kits, and so on. Every purchasable item both changes the player's economy (mining rate, storage cap, Rig Score) and appears as a real 3D model in a live Three.js battlestation scene.

This guide takes a completely uninformed person from a fresh checkout all the way to a new Rig Item live in production. You do not need to know JavaScript, 3D modelling, or game economics — every step is spelled out, with copy-paste commands and a full worked example at the end (§9).

The one-sentence summary. A Rig Item is one catalog row (price + economy stats, in PlayTools.html) plus one 3D model (a .glb file placed via rig_manifest.json). Add the row, drop in the model, position it, tune the price, preview, ship.

Do this once · ~15 minutes

You need three things on your computer: Git (to get and save the code), Node.js (to run the preview/editor tools), and a text editor (to edit the catalog). A modern web browser (Chrome/Edge/Firefox) is used for the 3D editor and preview.

Open a terminal (on Windows: "Git Bash" or PowerShell; on macOS/Linux: Terminal) and run:

What npm install pulls in. The repo's package.json lists the pipeline's dev dependencies: three (the 3D engine), playwright (drives the headless preview screenshots), @gltf-transform/cli (model compression), esbuild (bundles the in-app viewer), and @sparticuz/chromium (a fallback browser for preview). You do not call these directly — the npm run … scripts do.

02 The mental model — 4 places, 1 item ▾

Understand this and the rest is mechanical

A single Rig Item is described in up to four files. Each owns a different concern. Keep them straight and you'll never get lost:

FileOwnsYou edit it to…
CODE PlayTools.htmlThe catalog: the item's id, name, price, mining-rate / cap / Rig-Score effect, and store blurb. Also the global economy constants.Add the new item & set its economy stats.
3D assets/rig/models/<id>.glbThe actual 3D model file for the item.Drop the sourced/created model here.
3D assets/rig/rig_manifest.jsonThe placement: where the model sits, how it's rotated & scaled in the scene.Add a parts entry & tune its transform.
ECON DD/Rig_Economy_Tuner.htmlA balancing sandbox — simulates player wealth so you can sanity-check a price before shipping. Mirrors the catalog.Test pricing; export ready-to-paste rows.

2.1 How an id ties it all together

The magic glue is the item's id — one short lowercase string (e.g. desktoy, gpu2, monitor). The same id is used everywhere:

catalog row id:'lavalamp'  ⟷  model file models/lavalamp.glb  ⟷  manifest key "lavalamp": {…}  ⟷  the 3D-ownership set RIG3D_PARTS

If those four don't agree on the id, the item won't render. Pick the id once, use it consistently, and you're safe.

2.2 The three catalog buckets

Inside PlayTools.html the store is three arrays. Which array you add to depends on what the item is:

ArrayForExamples
PARTSFunctional hardware — internal PC parts that raise the mining rate or storage cap.GPU, CPU, RAM, Cooling, PSU
COSMETICSPeripherals & cosmetics — the visible battlestation items. Some peripherals carry a small mining bump; pure cosmetics are flex-only.Monitor, chair, keyboard, mouse, headset, posters, RGB, desk toys, books
SURFACESFloor & wall tiers — only one floor and one wall are equipped at a time (not additive).Hardwood floor, brick wall, synthwave mural

Most new items you'll add are cosmetics/peripherals (they have a visible model), so this guide's worked example targets COSMETICS. The mechanics are identical for PARTS; SURFACES are noted where they differ.

03 Step A — Add the NetStore item CODE ▾

Edit the catalog in PlayTools.html

This is the heart of it: one new line in an array. Open PlayTools.html in your editor and search (Ctrl/Cmd-F) for const COSMETICS (around line 2913) — or const PARTS for hardware (around line 2892).

3.1 The shape of a catalog row

Every row is a plain object. Here's a real one from the shipped catalog, annotated:

{ id:'desktoy', cat:'Cosmetic', name:'Desk Toy', cost:60, rate:0, cap:0, score:3, blurb:'A little kinetic figurine. Pure desk charm.' }
id
Unique lowercase key — the glue from §2.1. No spaces. This becomes models/<id>.glb and the manifest key. Choose carefully — it's hard to change later.
cat
A display category label (e.g. Cosmetic, Peripheral, Lighting, GPU). Groups items in the store UI.
name
The human-readable store name.
cost
Price in NetCoin. The single most important balance lever — see §6.
rate
How much this adds to the mining-rate multiplier (base is 1.0). 0.1 = +10% rate. Pure cosmetics use 0.
cap
How many hours it adds to the offline storage cap (base 12h). Usually 0 except RAM-type parts.
score
How much it adds to the Rig Score (the "how decked-out is my setup" flex number).
needs optional
An id this item is gated behind (e.g. a top GPU needs:'psu'). The player must own that first.
blurb
The one-line store description.
Honesty guardrail (from the design spec). NetCoin and Rig stats are an economy only — they never touch the player's skill rating ("Gamer Score" / GamerDNA). You can make an item rich-and-cool, never "better-aimed." Keep rate/cap modest for cosmetics.

3.2 Add your row

  1. Pick the right array. Visible peripheral/cosmetic → COSMETICS. Internal hardware that boosts mining → PARTS. Floor/wall → SURFACES (see §3.4).
  2. Insert a new row. Add it on its own line, keeping the array roughly sorted by ascending cost (the store displays in array order, and the tuner expects a price ramp).
  3. Fill the fields. Copy a neighbouring row, change id, name, cost, blurb, and the stats. Leave a trailing comma correct (every row except the last needs a comma after it).
  4. Save. That's the catalog done — the item is now buyable in the store.
JavaScript-syntax safety net. The catalog is real code, so a stray comma breaks the whole app (a blank page). Three rules cover 99% of mistakes: (1) strings use straight quotes '…', not curly "smart quotes"; (2) every field is separated by a comma; (3) every row except the very last in the array ends with a comma. After editing, open PlayTools.html in a browser — if it loads and the store shows your item, your syntax is fine.

3.3 Make the model render in-app (the RIG3D_PARTS set)

One extra wiring step the casual reader misses: the in-app 3D viewer only shows models for ids it's told are "3D parts." Search PlayTools.html for RIG3D_PARTS (around line 17539):

const RIG3D_PARTS = new Set(['chair','monitor','keyboard','headset','rgb','poster','desktoy',
    'books','poster_a','poster_b','poster_c','poster_d','poster_base']);

If your new item has a 3D model that should appear when owned, add its id to this set. (Pure economy items with no model — e.g. an internal RAM stick that isn't visible — can be left out.)

3.4 Special case — floor & wall (SURFACES)

Floors and walls work a little differently: only one of each is equipped at a time, and tier 1 is free/pre-owned. A surface row adds a kind ('floor' or 'wall') and a tier (1–3). They don't use .glb models — they're built procedurally in tools/rig-build.mjs (buildFloor/buildWall), so adding a brand-new surface variant also means adding a builder branch there. For your first item, stick to COSMETICS/PARTS.

04 Step B — Get a 3D model 3D ▾

Source a ready model OR create one — no 3D background needed

The item needs a model file: glTF 2.0 binary (.glb). A .glb is a single self-contained file that packs the geometry and the textures together — ideal for the web. You have three routes to one; pick whichever suits you.

4.1 The format rules (follow these and placement is painless)

PropertyRequirementWhy
Format.glb (glTF 2.0 binary), textures embeddedOne file, loads fast, no missing-texture issues.
MaterialsPBR metallic-roughness (baseColor + normal + roughness/metallic)Reacts correctly to the scene's lighting. Avoid Blender-only/proprietary shaders.
Up axisY-up (glTF default)Sits the right way up automatically.
ForwardFaces −Z (toward camera). If not, fix with rotY in the manifest.So it points at the viewer.
ScaleReal-world metres (desk ≈ 0.75 m tall, 27″ monitor ≈ 0.4 m). If wrong, fix with a manifest scale.Lands roughly life-size without fiddling.
OriginFurniture/floor items: origin at footprint centre, on the floor. Desk-top items: origin at the base resting point.Placing at y:0 sits it on the ground; desk items sit on the desktop.
Budget< ~50k triangles and ≤ 2K textures per itemWeb performance. Stylised low-poly is great (and tiny).
LicenseCC0 / CC-BY / purchased-with-redistribution. Note it in the manifest credit field.Legal to ship.
Namingmodels/<id>.glb where <id> matches your catalog id.The glue from §2.1.

4.2 Route 1 — Download a ready-made model easiest

The fastest path. Free, good-quality sources:

  • Sketchfab (sketchfab.com) — filter Downloadable + PBR, and prefer glTF downloads. Huge library.
  • Quaternius & Kenney — CC0 (no attribution required), stylised low-poly, tiny files. Great for desk toys, props.
  • Poly Pizza (poly.pizza) — CC0/CC-BY low-poly props.
  • Quixel Megascans — photoreal (heavier).
  • CGTrader / TurboSquid — paid; check the license allows redistribution.

If the download is already a .glb, you're done — skip to §4.5. If it's .gltf+folder, .fbx, or .obj, convert it (§4.4).

4.3 Route 2 — Generate from an image (AI image-to-3D) no modelling

Have a reference picture but no model? Image-to-3D tools turn a photo into a .glb:

  • Meshy (meshy.ai), Tripo (tripo3d.ai), Rodin — upload an image (or type a prompt), download the result as .glb.

Results vary; pick a clean, well-lit reference and you'll often get a usable prop in minutes. Then run it through the optimise step (§4.5) to shrink it.

4.4 Route 3 — Make/convert it in Blender (free) most control

Blender (blender.org) both creates models and converts other formats to .glb. Minimum viable workflow for a beginner:

  1. Open or import. File → Import your .fbx/.obj (or model something simple — a cube with bevels goes a long way for stylised props).
  2. Check scale & orientation. Set units to Metric/metres. Make the object roughly its real size (press N for the dimensions panel). Point its front toward −Y in Blender (Blender is Z-up; the glTF exporter rotates Z-up→Y-up for you, and "Blender −Y" becomes "glTF −Z front").
  3. Set the origin. Object → Set Origin → Origin to Geometry, then for floor items move the object so its base sits at Z=0 and re-set origin there (origin = footprint centre on the floor).
  4. Give it a PBR material. In the Shading tab, use a Principled BSDF material (that's the PBR metallic-roughness shader glTF expects).
  5. Export. File → Export → glTF 2.0 (.glb/.gltf). Choose format glTF Binary (.glb), tick +Y Up, and under Geometry enable Apply Modifiers & UVs/Normals. Save as <id>.glb.

Converting without modelling

If you only need to convert a format (not edit), the bundled CLI does it headlessly — no Blender:

# gltf-transform ships with the repo (via npm install). Convert + inspect:
npx gltf-transform copy input.gltf output.glb
npx gltf-transform inspect output.glb     # prints tris, textures, size

4.5 Optimise & compress (always do this before shipping)

Web users download these models, so size matters. The repo's chosen recipe (it took the whole model set from ~58 MB down to ~5 MB) compresses geometry with meshopt and textures to WebP:

npx gltf-transform optimize raw.glb assets/rig/models/<id>.glb \
  --compress meshopt --texture-compress webp

The runtime already bundles the meshopt decoder, so compressed models load with no extra setup. Aim for a final file in the low hundreds of KB where possible.

4.6 Drop it in place

Put the finished file at assets/rig/models/<id>.glb — the filename's <id> must exactly match your catalog id. That's the model installed; next we position it.

No model yet? You're not blocked. Two items render procedurally (in code, no .glb): the RGB Light Kit ("proc":"rgb") and a fallback poster. And the whole app has an SVG fallback when WebGL/3D isn't available. So you can ship the catalog row first and add the model later — the item just won't have a 3D mesh until you do.

05 Step C — Place & adjust it in the scene 3D ▾

The manifest + the interactive editor

Now we tell the scene where your model goes. This is the rig_manifest.json file. You can hand-edit the numbers, but the easy way is the interactive layout editor — drag sliders in a browser and export the result.

5.1 Add a manifest entry

Open assets/rig/rig_manifest.json. Under the "parts" object, add an entry keyed by your id:

"lavalamp": {
  "model": "models/lavalamp.glb",
  "on": "desk",                       // sits on the desktop (y auto-rests on the desk)
  "transform": { "pos": [-0.45, 0, -0.30], "rotY": 0, "scale": 1 },
  "credit": "Author Name / CC-BY"
}

The transform fields (how you "move things around")

pos [x,y,z]
Position in metres. x = left(−)/right(+), y = down/up, z = toward camera(+)/into scene(−). With "on":"desk" the y is handled for you (it rests on the desktop).
rotY / rotX
Rotation in degrees (yaw / pitch). Use rotY to spin a model to face the room.
scale
A single number (uniform) or [x,y,z]. Use if the model imported too big/small.
fitHeight
Auto-scale the model so it's exactly this many metres tall (handy when you don't know the source scale).
on:"desk"
Rest the item on the desktop surface instead of the floor.
replaces
A base item this swaps out when owned (e.g. the upgrade monitor replaces:"monitor_base").
screen
For monitors — which procedural screen image to show (e.g. "synthwave").
glow
Self-illuminate from the model's own colour (0–1) so flat art (posters) reads in the dark scene.
credit
License/attribution string — fill this in for every sourced model.
proc
Use instead of model for a code-built part (e.g. "proc":"rgb") — no .glb needed.

5.2 Position it visually with the editor

Hand-guessing coordinates is tedious. Instead:

  1. Launch the editor. Run npm run rig:edit and open http://127.0.0.1:8132 in your browser.
  2. Frame the camera. Drag to orbit, scroll to zoom — set up the hero angle.
  3. Select your part & drag its sliders. Pick the item, then live-drag its X/Y/Z, rotation, and scale until it sits right. Toggle other parts on/off to check for overlap. Tune bloom/FOV if needed.
  4. Export. Hit Export manifest JSON (copy or download) and paste the result back into assets/rig/rig_manifest.json, replacing the old contents.
Why the editor is trustworthy. The editor, the headless preview, and the real in-app viewer all share one scene builder (tools/rig-build.mjs). What you position in the editor is exactly what renders in the app — no surprises.

5.3 Quick visual check (headless)

To sanity-check without a browser, render a PNG:

npm run rig:preview                       # → tools/output/rig.png (all modelled parts)
node tools/rig-preview.mjs --own=lavalamp,chair,monitor   # a specific owned-set
node tools/rig-preview.mjs --contact          # a grid of every model (an "asset sheet")

Open the PNG, confirm your item sits correctly, tweak the transform, repeat. When it reads well, you're done with placement.

06 Step D — Tune the economy balance ECON ▾

Price it so it feels fair — using the tuner sandbox

An item's cost (and its rate/cap) decide how it fits the multi-week earning curve. To avoid guesswork, the repo ships a live balancing sandbox: DD/Rig_Economy_Tuner.html. Just open it in a browser — it's self-contained, no server needed.

6.1 What the tuner does

It mirrors the live catalog and simulates three player archetypes auto-reinvesting their NetCoin:

  • Grinder — returns daily and uses tools (gets the overclock bonus).
  • Regular — returns daily, claims the payout, doesn't grind tools.
  • Casual — every other day, so the streak keeps resetting.

Edit any parameter or catalog row and the summary, graphs, and an affordability table (which archetype can afford what, and on which day) all recompute instantly. That tells you whether your new item lands where you intend on the timeline.

6.2 Add & price your item in the tuner

  1. Open the tuner. Double-click DD/Rig_Economy_Tuner.html (or open it in your browser).
  2. Add a row. In the catalog table, add a row and fill id, name, description, cost, category, rate/cap/score, needs, and the model id (the rig_manifest.json key for its .glb; leave blank for procedural/no-model items).
  3. Watch the impact. The simulation updates — check the affordability day and the income-mix graphs. Nudge cost until the item lands at the intended point in the curve (e.g. an early cosmetic affordable in session 1; a flagship part at ~8 weeks).
  4. Export for NetStore. Click ⤓ Export for NetStore. It emits three ready-to-paste blocks: a PARTS row, a COSMETICS row (it splits by category exactly like the app), and a rig_manifest.json model stub.
  5. Paste them home. Drop the catalog row into PlayTools.html and the manifest stub into rig_manifest.json (then position it with rig:edit per §5).
Tuner ⇄ catalog: keep them mirrored. The tuner carries its own copy of the catalog (so it can run standalone). If you change a price in one place, change it in the other so the sandbox keeps telling the truth. The Export button is the clean way to keep them in sync.

6.3 The global economy knobs

Beyond per-item pricing, the whole economy is governed by a handful of named constants near the top of the Rig module in PlayTools.html (≈ line 2878). These are the same "baseline" values the design spec signed off, kept named so they're trivial to retune:

ConstantDefaultMeaning
BASE_RATE10NetCoin/hour at rig multiplier 1.0 (before any parts).
BASE_CAP_H12Offline accrual cap in hours before parts add storage.
DAILY_BASE100Day-1 streak payout.
STEP_PCT15+% of base added per consecutive day.
CAP_PCT150Streak-bonus cap (+150% → 2.5× around day 11).
OC_THRESH3Distinct applets/day needed to "overclock."
OC_BONUS25+% mining rate while overclocked.
MS_WEEKLY750Lump bonus at streak day 7 / 14 / 21 …
MS_MONTHLY5000Lump bonus at streak day 30 / 60 / 90 …
Change global knobs sparingly. Per-item cost tunes one item; these constants reshape the entire curve for every player. Adjust them only with a deliberate rebalance, and re-run the tuner afterwards.

07 Step E — Preview it in the real app 3D ▾

See the item in The Rig, in true 3D, exactly as players will

The headless PNG (§5.3) checks placement, but to see the item in the actual store and battlestation you serve the app:

  1. Start the server. Run npm run serve, then open http://127.0.0.1:8133/PlayTools.html.
  2. Go to The Rig. In the app nav, open The Rig (route #/rig). Served this way, the battlestation renders in real 3D (lazy-loaded), bound to the parts you own.
  3. Buy your item. Open the NetStore (#/rig/store) and purchase it. (Need NetCoin to test? The store/economy is local; you can grant yourself coins via the app's dev affordances or just let idle/daily accrue.) Confirm it appears in the store with the right name/price/blurb and renders in the scene once owned.
Why serve instead of double-clicking? Opened directly from disk (file://), the app can't fetch the model assets, so it falls back to the procedural SVG battlestation. The serve script wires up three.js and the assets/rig paths so the real 3D viewer loads. No WebGL → it still gracefully falls back to SVG.

7.1 Pre-flight checklist

Tick these off before you ship (click to mark done — saved in your browser):

  • Catalog row added to the correct array (PARTS/COSMETICS/SURFACES), syntax valid (app loads).
  • Item shows in the NetStore with correct name, price & blurb.
  • Model file at assets/rig/models/<id>.glb, optimised/compressed.
  • Manifest parts entry added; transform tuned in rig:edit.
  • Id added to RIG3D_PARTS (if it has a visible model).
  • Price sanity-checked in the economy tuner.
  • Verified in-app via npm run serve: buys correctly & renders in the scene.
  • credit/license noted in the manifest entry.

08 Step F — Bundle, commit & deploy SHIP ▾

From your branch to the live site

8.1 Do you need to re-bundle?

The in-app 3D viewer is shipped as a pre-built bundle, tools/rig-inapp.bundle.js (three.js inlined, so the browser doesn't fetch it at runtime). Most item additions do NOT need a re-bundle — the bundle reads the manifest & models at runtime, so new catalog rows, new models, and manifest edits work without rebuilding.

You only re-bundle if you changed the viewer/builder code itself (tools/rig-inapp.mjs or tools/rig-build.mjs — e.g. you added a new "proc" builder or a new SURFACES variant). In that case:

npm run rig:bundle     # → rebuilds tools/rig-inapp.bundle.js

8.2 Commit your changes

Stage everything you touched and commit with a clear message:

git add PlayTools.html assets/rig/rig_manifest.json assets/rig/models/<id>.glb
# (also DD/Rig_Economy_Tuner.html if you re-priced there, and the bundle if you rebuilt it)
git commit -m "Add <Item Name> to the NetStore (catalog + 3D model + placement)"
git push -u origin my-new-rig-item

Then open a pull request against main for review.

8.3 How production deploy works

Deployment is automatic. The workflow .github/workflows/deploy.yml runs when changes land on main (via your merged PR) that touch any of these paths:

PlayTools.html
tools/rig-inapp.bundle.js
assets/rig/**

On a qualifying push it FTPs the app + viewer bundle + the whole assets/rig/ tree (manifest and all models) to the Hostinger host, preserving relative paths so the app's ./tools and ../assets URLs resolve in production. Because your new model lives under assets/rig/models/ and your catalog edit is in PlayTools.html, both are picked up automatically — no manual upload.

What you changedGets deployed because…
Catalog row, RIG3D_PARTS, economy constantsthey're in PlayTools.html (a watched path).
New .glb modelit's under assets/rig/** (watched); the deploy loops over assets/rig/models/*.
Manifest placementassets/rig/rig_manifest.json is under assets/rig/**.
Viewer/builder codeyou re-bundled, and tools/rig-inapp.bundle.js is a watched path.
The economy tuner does not deploy. DD/Rig_Economy_Tuner.html is a design/dev sandbox, not part of the watched deploy paths — it lives in the repo for the team, not on the live site. That's expected: the app ships, the tuner stays internal.

Manual deploy. The workflow also supports workflow_dispatch (a "Run workflow" button in GitHub Actions) if you ever need to re-push without a new commit. Use it only when you know the FTP credentials/secrets are configured.

09 Full worked example — add a "Lava Lamp" ▾

Every step, start to finish, nothing skipped

Goal: add a cheap, charming desk cosmetic — a Lava Lamp — that's a pure flex item (no mining bump) affordable in the player's first session.

① Decide the item

id
lavalamp
name
Lava Lamp
type
desk cosmetic → goes in COSMETICS
price
~75 NetCoin (early, session-1 affordable)
stats
rate 0, cap 0, score 3 (pure flex)

② Add the catalog row CODE

In PlayTools.html, find const COSMETICS and add (kept in ascending-cost order, near the other cheap cosmetics):

{ id:'lavalamp', cat:'Cosmetic', name:'Lava Lamp', cost:75, rate:0, cap:0, score:3, blurb:'A slow-bubbling retro glow for the desk. Pure vibe.' },

③ Register it for 3D CODE

Find RIG3D_PARTS and add 'lavalamp' to the set so the in-app viewer shows the model when owned:

const RIG3D_PARTS = new Set(['chair','monitor','keyboard','headset','rgb','poster','desktoy',
    'books','poster_a','poster_b','poster_c','poster_d','poster_base','lavalamp']);

④ Get the model 3D

Grab a CC0 lava-lamp from Poly Pizza / Sketchfab (or generate one with Meshy from a reference photo). Optimise & save it:

npx gltf-transform optimize lavalamp-raw.glb assets/rig/models/lavalamp.glb \
  --compress meshopt --texture-compress webp

⑤ Place it 3D

Add a manifest entry under "parts" in rig_manifest.json, then refine with npm run rig:edit:

"lavalamp": {
  "model": "models/lavalamp.glb",
  "on": "desk",
  "transform": { "pos": [-0.5, 0, -0.45], "rotY": 12, "fitHeight": 0.22 },
  "glow": 0.4,
  "credit": "Author Name / CC0"
}

(A lamp glows, so a little glow makes it read in the dark scene. fitHeight locks it to 22 cm tall regardless of the source model's scale.)

⑥ Balance-check ECON

Open DD/Rig_Economy_Tuner.html, add the same row (model id lavalamp), confirm a session-1 player can afford 75 NetCoin early, and Export for NetStore to double-check your pasted rows match.

⑦ Preview 3D

npm run rig:preview                          # quick PNG
npm run serve                                # then open #/rig, buy the Lava Lamp, see it glow on the desk

⑧ Ship SHIP

git add PlayTools.html assets/rig/rig_manifest.json assets/rig/models/lavalamp.glb
git commit -m "Add Lava Lamp desk cosmetic to the NetStore"
git push -u origin my-new-rig-item
# open a PR → merge to main → deploy.yml FTPs it live automatically
That's a complete item. No re-bundle was needed (no viewer-code change), and the deploy picks up both the PlayTools.html edit and the new model under assets/rig/** on merge to main.

10.3 Scene block (top of the manifest)

You rarely touch these, but for completeness: scene.hdri (lighting environment), scene.camera (pos/target/fov + orbit limits), scene.bloom (glow post-process), and scene.wall (the dark back wall posters hang on). Tune them in rig:edit and export.

11 Troubleshooting & FAQ ▾

When something doesn't show up
SymptomLikely cause & fix
The whole app is blank / white.A JavaScript syntax slip in the catalog — a smart-quote, a missing/extra comma. Re-check your row (§3.2). Open the browser console (F12) for the line number.
Item shows in the store but no 3D model.(a) Id missing from RIG3D_PARTS (§3.3); (b) no manifest parts entry; (c) the model path / filename doesn't match the id; (d) you opened the app from file:// — use npm run serve.
Model appears but is huge / tiny / sideways / sunk into the desk.Transform issue — fix scale/fitHeight, rotY, and pos in rig:edit. For "sunk", check the model's origin (§4.1) or add "on":"desk".
Model is dark / unlit / wrong colour.Not a PBR metallic-roughness material. Re-export with a Principled BSDF (§4.4). For flat art, add a glow value.
Model loads slowly / huge file.Skip the optimise step? Run the gltf-transform optimize … --compress meshopt --texture-compress webp recipe (§4.5).
npm run rig:preview errors / blank PNG.Headless Chromium/WebGL hiccup or a model failed to load. Re-run; check the console output it prints (it lists scene errors and per-model sizes). Ensure npm install completed.
Editor/preview show it, but the live site doesn't.The deploy only runs on push to main touching watched paths. Confirm your PR merged and the Action ran (§8.3).
Price feels off in the curve.Re-tune cost in the economy tuner and re-export (§6).

FAQ

Do I have to provide a 3D model?

No — you can ship the catalog row first; the item just won't have a mesh until you add one. The RGB kit and a fallback poster are even fully procedural (no .glb).

Can I change an item's id later?

Avoid it. The id is the glue across the catalog, the model filename, the manifest, and player save data. Changing it orphans existing owners' saved purchases. Pick a good id up front.

Will adding an item break existing players' saves?

No — saves are keyed by owned ids in localStorage. New items simply appear as not-yet-owned.

Do I ever edit the bundle by hand?

Never. tools/rig-inapp.bundle.js is generated by npm run rig:bundle. Hand edits are overwritten on the next build.
